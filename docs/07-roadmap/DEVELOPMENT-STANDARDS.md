# Lumora Development Standards

> Status: Proposal, pending approval. Source of truth: Phase 2 PRD and Phase 1 docs.

These are proposals; the owner may override any of them in review. Related: [IMPLEMENTATION-PLAN.md](IMPLEMENTATION-PLAN.md), [TESTING-STRATEGY.md](TESTING-STRATEGY.md), [DEFINITION-OF-DONE.md](DEFINITION-OF-DONE.md).

## 1. Git workflow

| Rule | Standard |
|---|---|
| Model | Trunk-based. `main` is always deployable and protected |
| Branches | Short-lived: `feat/<milestone-id>-<slug>`, `fix/<slug>`, `docs/<slug>`, `chore/<slug>`. Example: `feat/m06-session-day-allocation` |
| Pull requests | Required for every change; CI green; squash merge |
| Milestone size | One milestone is several pull requests, split by the slices in IMPLEMENTATION-PLAN.md section 2 |
| Tags | `m<NN>-done` when the Definition of Done is met. Release tags are semver: `v0.<n>.0` before MVP, `v1.0.0` at M15 |
| Later phases | Phase 2 and Phase 3 code merges to `main` behind configuration flags |

## 2. Commit messages

Conventional Commits: `type(scope): subject`.

- Types: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `build`, `ci`, `chore`.
- Scope: a module name (for example `timer`, `sessions`) or `shared`, `ci`, `db`, `docs`.
- Body states why, not what.
- Footer references FR, NFR and milestone ids (`Refs: FR-054, NFR-052, M07`).
- Breaking changes are marked with `!` and a `BREAKING CHANGE:` footer.

## 3. Code quality

- Strict TypeScript. No `any` without a comment stating why.
- Zod schemas shared between client and server; the server validates all input.
- Dependency boundaries are enforced by tooling (MODULE-BOUNDARIES section 8); a module never reads another module's persistence.
- Server components by default; client components only for interactivity (ADR-001 consequence).
- No new dependency without a line in the TECHNOLOGY-DECISIONS review. Avoid unnecessary abstractions.
- Numeric defaults and limits are named constants from the configuration module; no magic numbers.
- Time logic only through the time module (ADR-006).
- Drizzle and Better Auth versions are pinned (ADR-001).

## 4. Linting and formatting

ESLint with the TypeScript and accessibility plugins and the boundary rule; Prettier for formatting. Both run in CI stage 2 and as a pre-commit hook.

## 5. Type checking

`tsc --noEmit` in strict mode for web, worker and tests in CI stage 1.

## 6. Coverage

Domain at least 90% line, application at least 80%, overall at least 80%. The ratchet never decreases. Coverage is a floor; BR, NFR and AC traceability is the real gate.

## 7. Documentation

- A milestone pull request updates the documents it changes: SDD, DATA-DICTIONARY, API-ENDPOINTS, OpenAPI once generated, PAGE-SPECIFICATIONS, and the checklist in MILESTONES.md.
- An architectural change needs an ADR amendment and approval (Build Mode: no major architecture change without approval).
- A changelog entry is written per release.

## 8. Migrations

From DATABASE-DESIGN section 2 and BACKUP-RESTORE:

- drizzle-kit generated SQL is committed; migrations are forward-only.
- Expand/contract only. A contract migration ships one release after its expand.
- A separate migration step runs under the owner role before traffic; the application role has DML only.
- Each milestone migrates only its own tables.
- Enumerations are text with CHECK constraints; no PostgreSQL ENUM.
- Identifiers are UUIDv7 generated by the application (or the Better Auth adapter if M00 spike (b) fails).
- The latest restorable point is recorded before every production migration.
- The pg-boss schema is excluded from application migrations.

## 9. Secrets and configuration

- Secrets and environment settings come from the secrets store at runtime; nothing in the repository or the client bundle (NFR-019).
- Behavioral defaults live in the configuration module and are identical in every environment.
- `.env` files for local use are git-ignored; an example file lists names without values.

## 10. Logging

- pino, structured, one request id per request.
- Never log passwords, tokens, session ids, API keys or note content (NFR-063).
- Error tracking applies the same scrubbing (U-A7).

## 11. Review checklist

A reviewer verifies:

1. Scope matches one milestone; no future-phase behavior reachable.
2. Server-side validation on every input; error codes match API-ERRORS.md.
3. Ownership check and a contract test for each resource.
4. Idempotency and concurrency where the endpoint spec requires them.
5. Migrations are backward-compatible and touch only this milestone's tables.
6. Purge handler and export contributor registered for new user-data tables.
7. Accessibility: keyboard path, labels, contrast, 360 px.
8. Tests cover the BR, NFR and AC ids claimed; no tests of wiring or echoes.
9. No secrets or personal data in logs.
10. Docs updated; no new dependency without a decision record.
