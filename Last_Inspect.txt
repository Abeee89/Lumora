# LUMORA — APPROVED DOCUMENTATION CORRECTION

You are acting as a Senior Software Architect, Technical Documentation Engineer, and Requirements Engineer for the Lumora project.

## Objective

Apply the explicitly approved Owner Decision Matrix from the latest Phase 8 audit preparation to the existing Lumora documentation.

This task is strictly documentation correction. Do not implement application code.

## Step 1 — Inspect the project

Inspect the following sources:

- `Build Mode.md`
- `README.md`
- `DOCUMENTATION-INDEX.md`
- `docs/FINAL-ARCHITECTURE-REVIEW.md`
- `docs/IMPLEMENTATION-READINESS.md`
- `docs/TRACEABILITY-MATRIX.md`
- `docs/OPEN-DECISIONS.md`
- All Phase 1–8 documentation
- All ADR files
- The latest approved Owner Decision Matrix and approval record

Use the actual repository files as the source of truth. Do not assume that a previously discussed decision has been recorded.

## Step 2 — Verify owner decisions

Verify the explicit approval status of:

- C-1 through C-6
- S-1 through S-5
- M-1 through M-31
- M00-A through M00-F

For each decision, record:

- Finding ID
- Selected option
- Owner approval evidence
- Approval date, if recorded
- Affected documents
- Required correction
- Status

If an option is not explicitly recorded, do not guess. Mark it as `OWNER DECISION REQUIRED`.

## Step 3 — Apply corrections

Use the approved resolution bundles:

- B1 Authentication
- B2 Foundation data/jobs
- B3 Privacy/recovery/export
- B4 Plan/timer correctness
- B5 Product rules
- B6 Public/API contracts
- B7 Accessibility/UI
- B8 Roadmap/testing
- B9 Governance

Follow the dependency map and recommended correction order.

Preserve all existing requirement IDs, ADR IDs, milestone IDs, and decision IDs unless an approved decision explicitly requires a change.

## Step 4 — Documentation consistency

Verify consistency across:

- PRD and Functional Requirements
- Business Rules and Edge Cases
- Non-Functional Requirements
- SDD and Architecture
- ADRs
- Database design and lifecycle
- UI/UX specifications
- API and integration contracts
- Roadmap and milestones
- Testing strategy and Definition of Done
- Traceability and implementation readiness

No contradictory requirement, schema, API contract, UI behavior, or milestone dependency may remain silently unresolved.

## Step 5 — Governance

Update:

- `OPEN-DECISIONS.md`
- `TRACEABILITY-MATRIX.md`
- `IMPLEMENTATION-READINESS.md`
- `FINAL-ARCHITECTURE-REVIEW.md`
- `CHANGELOG.md`
- `DOCUMENTATION-INDEX.md`

Preserve the difference between globally blocking decisions and decisions that only block a future milestone.

Do not mark an ADR as Accepted without explicit owner approval.

## Restrictions

- Documentation only.
- No application code.
- No package installation.
- No database migrations or schema implementation.
- No M00 technical experiments.
- No Build Mode implementation.
- Do not invent owner approval.
- Do not delete historical decisions or audit findings.

## Required output

1. Approved Decision Verification Report
2. Correction Log grouped by B1–B9
3. Updated document inventory
4. Remaining unresolved decisions
5. Cross-document consistency report
6. Recommended next action

Stop and wait for owner review.
